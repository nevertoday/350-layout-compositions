01

广度与深度的代价

BREADTH VS. DEPTH IN HIERARCHIES

海报第一条要点直指树形布局最容易失控的变量：「控制层级深度，通常不超过 4 层，保持结构简洁。」这并非拍脑袋的审美洁癖，而是几十年人机交互实验反复验证的认知规律。

早在 1984 年，John I. Kiger 在 64 个终点条目的菜单结构实验中，对比了深而窄（如 26 六层）与宽而浅（如 82 两层）五种树形：层级越深，寻找目标耗时越长、走错分支后反复回退的概率越高。1998 年，微软研究院的 Kevin Larson 与 Mary Czerwinski 在 ACM CHI 上测试了 512 项百科层级，同样发现两层宽浅结构显著快于三层深窄结构——只要分类命名透出清晰的「信息气味」，人眼扫描 16 项平级分类远比连续点穿多层目录轻松。

经验值，并非铁律

「不超过 4 层」适用于大多数知识库、后台菜单和内容导航；但如果面对大型代码仓库、操作系统目录或法律条文，深层结构无法强行删减。这时与其硬砍层级，不如补上默认折叠无关支线、固定面包屑与留路径搜索，把用户从迷路边缘拉回来。

02

五种视觉线索怎么分工

VISUAL CUES & ANATOMY OF A TREE

一棵好读的目录树看起来轻巧，其实由五层互相咬合的视觉信号共同支撑：缩进阶梯标明谁在谁里面，纵横引导线让隔着十几行的远亲也能一眼认出父节点，类型图标把「能展开的容器」和「末端文档」在 0.2 秒内分开，数量徽标提前预告展开后的体量，展开符（− / +）则给出明确的点击落点。

关掉旁边任意几枚图层开关试试看：哪怕数据还是同一棵树，只要撤掉两三层视觉线索，原本井然有序的「知识库」就会迅速退化成难以扫描的纯文本堆。

03

键盘与无障碍协议

WAI-ARIA TREE VIEW INTERACTION

树形浏览是 Web 无障碍里最容易写错的模式之一。如果把几十个树节点都做成普通链接，键盘用户必须连续按几十次 Tab 才能跨过侧栏。W3C WAI-ARIA Authoring Practices Guide（APG）为此规定了严格的游走焦点（Roving Tabindex）模型：整棵树只占 1 个 Tab 停靠点，进入后完全交由方向键控制。

W3C 官方提醒：如果你的页面只是普通官网的多级导航菜单，请优先使用更轻量的折叠面板（Disclosure），不要轻易套用 role="tree"；只有当用户像操作文件浏览器或 IDE 目录那样深度检索层级时，才启用完整树形键盘协议。

小屏幕怎么不挤扁

          
MOBILE ADAPTATION & CONTEXTUAL SEARCH

        

      


      

        

          
海报第五条要点写得很实在：「在小屏幕下支持折叠、面包屑或搜索，保持可用性。」桌面端 260px 的树形侧栏一旦搬到 375px 手机竖屏，四级缩进加图标就能吞掉将近一半宽度，长标题立刻被挤压折断。

          
解决窄屏树形浏览有三条主流路径：用抽屉折叠把目录让位给正文；用单层钻取加顶部面包屑把二维嵌套拉平为一维清单，每层享有 100% 宽度；以及配一个保留祖先路径的搜索框——千万别把匹配结果孤零零甩出来，用户需要看到它藏在哪一支下面。

什么时候别用树形

          
WHEN NOT TO USE A TREE BROWSER

        

      


      
树形浏览布局建立在一个硬前提上：每条内容大致归属一个明确的上级，且信息足够多、需要逐层收拢。一旦数据结构违背这个前提，强塞进树里反而会把产品做难用。


      

        

        

      


      
      

        

          
多维属性交叉筛选

          
商品或素材同时具备颜色、尺码、价格等多个维度时，改用 卡片网格布局 或 搜索结果布局。

        

        

          
并列对比与排序统计

          
需要按列对齐数值、批量排序或看宏观指标时，优先选用 数据表格布局 或 仪表盘布局。

        

        

          
按阶段或时间推进

          
工作流状态适合 看板布局，日程排期适合 日历布局，线性历程交给 时间线布局，多步录入用 分步表单。

        

        

          
极浅结构或视觉陈列

          
只有 1–2 层轻导航用 分层导航布局 或 设置页面布局；偏重图文陈列则交由 画廊布局 与 便当盒布局。
