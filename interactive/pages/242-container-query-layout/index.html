01

          
同一张卡，三种宽

          
Same card, three widths

          
原海报把核心拆成三句话：以容器为准、组件自治、局部响应。

        


        

          
传统响应式布局习惯按浏览器窗口宽度切版，但真正写组件库时，同一张产品卡或摘要卡常常同时被塞进侧边栏、双栏网格和顶部焦点区。窗口一直停在 1280px 没动过，三张卡拿到手的可用宽度却差了两三倍。


          
    
            
  • 
              CONTAINER
              
    以容器为准
    
              
    “突破视口限制”
    
              
    判断条件不再看 @media 里的整块屏幕，而是看最近一层声明了 container-type 的祖先容器宽度。
    
            
    • 
            
  • 
              COMPONENT
              
    组件自治
    
              
    “独立决策与适配”
    
              
    不必再写 .sidebar .card、.modal .card 这类页面特例；组件自己带着窄、中、宽三套规则，搬去哪儿都成立。
    
            
    • 
            
  • 
              QUERY
              
    局部响应
    
              
    “只对容器变化响应”
    
              
    用户折叠侧栏、拉宽分屏或打开抽屉时，只有宽度变了的那一格重排，同屏其余组件纹丝不动。
    
            
    • 
          


          

            
边界说明 · 补全海报原话

            
原海报提到容器查询可按“容器的尺寸与状态”调整样式，值得分两步看：尺寸查询（width / inline-size 与 cqi 单位）已于 2023 年 2 月进入全浏览器 Baseline 2023，生产环境可放心使用；而样式查询（style()）与滚动状态查询（scroll-state()，2025 年才先在 Chromium 133 落地）跨浏览器支持仍在陆续补齐，现阶段只适合作为渐进增强。此外，组件无法查询自身宽高，必须由外层容器先声明 container-type。

02

          
为什么等了十二年

          
Where it comes from

          
前端从 2011 年就想要它，真正卡住浏览器的是“布局死循环”。

        


        

          
早在响应式网页刚流行时，开发者就发现视口媒体查询解决不了复用组件的问题。但浏览器引擎的传统流水线是单向的：先算样式，再算布局。如果一个盒子能查询自己的尺寸来改样式，样式一变又反过来改变尺寸，排版就会在两帧之间永远震荡。


          
    
            
  1. 2011
    Andy Hume 提出 Selector Queries：较早用脚本演示按父容器宽度切换组件样式的思路，点出组件级响应的刚需。
    2. 
            
  2. 2013–14
    “元素查询”热潮撞上循环墙：社区做出 css-element-queries 等脚本垫片，却暴露出元素自查尺寸导致无限重排的逻辑死结。
    3. 
            
  3. 2015
    Mat Marquis 与 RICG 改道“容器查询”：2015 年 6 月在 A List Apart 发表《Container Queries: Once More Unto the Breach》，正式放弃“查自己”，改为“查祖先容器”。
    4. 
            
  4. 2020
    David Baron 提出隔离解：Mozilla 工程师 David Baron 发布实现路径方案，借助 CSS Containment 单轴尺寸隔离切断子级反推父宽的回环。
    5. 
            
  5. 2021
    Miriam Suzanne 执笔 W3C 草案：CSS 工作组采纳提案并由 Miriam Suzanne 共同编辑《CSS Containment Module Level 3》，2021 年 12 月发布首个公开工作草案（条件语法后并入 CSS Conditional Rules Level 5）。
    6. 
            
  6. 2022–23
    进入 Baseline 2023：Chrome / Edge 105 与 Safari 16 于 2022 年 9 月率先支持，Firefox 110 于 2023 年 2 月补齐，尺寸容器查询与容器单位全主流浏览器可用。
    7.

03

          
容器里的尺子：cqi

          
Container query units

          
@container 管结构换档，cqi 管字号与留白平滑呼吸。

        


        

          
容器查询不仅带来了条件语句，还配套了六枚容器相对单位：cqi（行内尺寸的 1%，横排文字下即宽度）、cqb（块级尺寸 1%）、cqw、cqh、cqmin 与 cqmax。它们把“字号随容器宽微调”从硬写多道断点里解放了出来。

在 1440px 大屏的窄侧栏里，cqi 只乘当前槽宽，标题绝不会盲目膨胀。

                

              


              

                

                  标题字号
                  

                  16.2px
                

                

                  水平内边距
                  

                  16.2px
                

                

                  字宽舒适度
                  

                  适中
                

                
cqi 始终以当前容器宽度为 100 份，配合 clamp() 设好上下限，既防止极窄槽字太小，也防止宽屏字太大。

              

            

          


          
    
            
  • cqi容器行内轴（横排即宽）的 1%，最常用，适配多语言书写方向
    • 
            
  • cqb容器块级轴（横排即高）的 1%，需搭配 container-type: size
    • 
            
  • cqmin / cqmax取 cqi 与 cqb 的较小值或较大值，适合方形徽章

04

          
两个最容易踩的坑

          
Two classic pitfalls

          
九成容器查询故障，出在选错隔离轴与忽略包含块副作用。

        


        

          
容器查询背后的基石是 CSS Containment。一旦你给父盒写上 container-type，浏览器会同时启用布局隔离与样式隔离——这既切断了死循环，也会悄悄改变两件日常行为。


          

            
            

              

                TRAP 01
                
写 size 忘了定高，容器塌成 0px

              

              
除非真要查询容器高度，否则永远优先写 inline-size。点击下面开关看高度如何变化：

              

                
                
                
              

              

                

                  

                    产品公告卡
                    
文字内容原本需要约 92px 高度自然撑开容器。

                  

                

              

              
当前实测容器高：0px（已塌陷）——size 切断了内容撑高通道，内部文字溢出到容器外面。

            


            
            

              

                TRAP 02
                
容器形成新包含块，关住 fixed 弹窗

              

              
布局隔离会让容器变成后代 position: fixed 元素的定位基准，还会建立新的层叠上下文。点下面开关对比：

              

                
                
              

              

                

                  container-type: inline-size
                  
卡片正文区域

                  

                    操作菜单（被困）
                    被裁切/锁死在容器框里
                  

                

                

                  操作菜单（自由定位）
                  脱离容器隔离层，完整浮在视口上方
                

              

              
留在声明了 container-type 的父盒内时，全屏遮罩或下拉浮层会被新包含块锁在卡片边框里。

            

          

        

      

    

  


  
  

    

      

        

          
05

          
何时用，何时别用

          
When to use, when not

          
页面骨架归视口，复用组件归容器，别拿一把锤子敲所有钉子。

        


        

          
容器查询不是来取代媒体查询的，而是补上现代界面的“微观层”：页面级整体结构仍交给240 响应式布局或按屏换模板的241 自适应布局，外框的缩放规则交给239 流体布局或238 固定宽度布局，容器内部元素怎么排仍由226 弹性盒布局和227 网格布局执行——242 专管“同一个组件落进不同宽槽位时怎样自主变身”。


          

            

              NOT 01
              
别用在靠内容撑宽的元素

              
胶囊按钮、标签芯片、行内徽章的宽度本来就靠字数撑开；给它们套 inline-size 会切断内容测宽，盒子瞬间缩成 0px。

            

            

              NOT 02
              
别拿它管整站宏观壳层

              
顶栏切换汉堡菜单、隐藏全局侧边导航，本来就取决于整块浏览器窗口宽，直接写 @media 更直观且不引入隔离副作用。

            

            

              NOT 03
              
别指望它跨卡对齐内部行线

              
想让并排三张卡片的标题、正文、价格行严格对齐，应先看228 子网格布局；container-type 的布局隔离会阻断子网格轨道传递。

            

            

              NOT 04
              
只换列数不改结构时不必写

              
如果只是等宽图片网格按空间自动增减列数、卡片内部结构一成不变，一行 repeat(auto-fit, minmax(240px, 1fr)) 更省事。

            

          


          
          

            

              

                
需求分拣台：这 6 个任务该交谁？

                
点击任意一张真实界面需求卡，看是否该用容器查询以及最短写法。

              

            

            

              
              
              
              
              
              
            

            

              

                用 @container
                典型主角场景：给外层插槽挂 inline-size
              

              
侧栏和主区处在同一个 1440px 窗口里，@media 根本分不出谁宽谁窄；把查询交给容器，卡片就能在两个位置各用最合适的排法。

              
.slot { container-type: inline-size; }
@container (width >= 400px) { .card { display: grid; grid-template-columns: 140px 1fr; } }
